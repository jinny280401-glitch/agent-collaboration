# Engram:跨 Agent 记忆共享

多个 agent 协作时,每个 agent 各自踩的坑如果不共享,就会被反复重踩。Engram 是一个本地 HTTP 记忆服务,让不同 agent 把**可跨会话复用的教训**写进同一个库,别的 agent 下次就能读到。

## 架构

- 本地 HTTP 服务,token 鉴权(`X-API-Token` header)。
- 开机自启(launchd)。
- 不直接操作底层文件(有锁 / 版本迁移 / schema 校验),所有读写走 API。

## 各 Agent 接入方式

| Agent | 方式 | 实时性 |
|---|---|---|
| Claude Code | MCP 自动读取 | 实时 |
| Codex | 本机可走 HTTP API 读写,平时拿静态快照 | 快照 |
| ChatGPT | 云端看不到 localhost,靠导出的 Custom Instructions 文本 | 手动同步 |

**边界**:只有本机实时读取的 agent 永远最新;云端 agent 读的是快照,不是实时同步。

## 写什么形态(决定 Engram 收不收)

这是整个系统最反直觉、也最值得共享的一条:**Engram 会拒收"World State / Runtime State"**。

写"事件 / 项目状态"会被拒,必须写"**教训 + 根因 + how to apply**"。

| 形态 | 例子 | 结果 |
|---|---|---|
| ❌ 事件 / 项目状态 | "某模块补完文档""项目封存 C 段""某台机器 HTTPS 出口死了" | 拒(World State) |
| ✅ 教训 / 根因 / 可复用原则 | "写完 skill 必须先基线测试,否则等于没做""海外 API 域名调用前先验通" | 收 |

**自检问题**:写之前问自己——

> 这条信息能帮另一个 agent 在**不同项目**上避免同类错误吗?

- 不能 → 改写成"教训"形态再写
- 能 → 直接写
- 写的是某台机器当下的网络 / 服务状态 → 不写,留本地记忆文件

## 分类器的实测规律(踩坑沉淀)

Engram 的过滤器是**规则分类器**,不是纯语义模型。多次实测后的规律:

1. **summary 字段是分类器主要看的字段**,detail 里加什么都不影响判定。
2. summary 若含**流程状态名**(AUTHORIZED / EXECUTED / DEPLOYED / PASS / BLOCKED / verdict / Status)或 `X ≠ Y ≠ Z` 且成分是状态标签 → 大概率被判 World State。
3. 写成**动作 / 推理关系**(跑探针 = validation 已开始;判断…只能看…不能…)更容易通过。
4. 被拒后的**覆盖手段**:summary 加 `规则:` / `原则:` 前缀重写一次。这是补救,不是第一选择。
5. **只给一次重写机会**。再拒就降级到本地记忆文件,不要用 curl 循环猜分类器——那等于把分类器当黑盒暴力试。

> claim 上限提醒:上面是对**本机这台 Engram filter** 的观察规律,不是 Engram 系统层面的永久契约。换一台部署可能不同。

## 两层写入机制

- **层 1 主动写入**(高质量):完成部署 / 改配置 / 修 bug / 做架构决策后,主动 POST 一条教训。
- **层 2 Stop hook 兜底**(自动):会话结束时 hook 抓最后一轮对话写入兜底 domain。防的是"该写忘了写"。

## 不需要写入的情况

纯查询、解释代码、回答问题、临时调试。
